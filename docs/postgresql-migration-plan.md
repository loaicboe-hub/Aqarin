## 1. Executive Summary & Verification Scope

This document provides a forensically validated technical blueprint for migrating the AQAR IN real estate platform from MySQL 8.4 to **PostgreSQL 16 with PostGIS 3.4**. 

### Critical Validations & Policy Enforcements:
1. **No False Zero-Downtime Claims:** The migration will NOT claim "zero downtime." It employs a **controlled 10-minute maintenance window (Write-Freeze)** scheduled at off-peak hours (03:00 AM Cairo Time) to ensure mathematical zero data loss.
2. **PostGIS Unit-Safe Semantics:** Spatial queries are corrected to use true **`GEOGRAPHY(Point, 4326)`** semantics for meter-based distance calculations (`ST_DWithin`), preventing critical degree-to-meter conversion bugs.
3. **No Naive "DB_CLIENT Switch" Assumption:** Rollback limitations and code incompatibility realities are explicitly documented. The backend cannot switch back to MySQL via an environment variable without a dedicated abstraction layer; a formal disaster-recovery and write-reconciliation protocol is defined.
4. **Data & Hash Preservation:** Strategy for preserving all existing property IDs, user accounts, and bcrypt hashes without invalidating client credentials.

## 2. Technical Incompatibilities & Code-Level Dialect Mapping

The existing Node.js Express backend currently executes raw SQL queries via `mysql2`. The table below documents the concrete dialect differences and the mandatory code changes:

| Architectural Component | Existing MySQL 8.4 Implementation | Target PostgreSQL 16 + PostGIS Implementation | Code Refactoring Required |
| :--- | :--- | :--- | :--- |
| **Driver Package** | `mysql2/promise` (`server/src/db.js`) | `pg` (`node-postgres`) with connection pooling (`pg.Pool`) | Replace `import mysql from 'mysql2/promise'` with `import pg from 'pg'`. |
| **Parameter Placeholders** | Positional question marks: `WHERE id = ? AND status = ?` | Numeric positional placeholders: `WHERE id = $1 AND status = $2` | Refactor every SQL query string in all 6 route files to use `$1, $2...`. |
| **Insert Return Value** | `const [result] = await pool.query(...)`<br>`result.insertId` | Query appended with `RETURNING id`<br>`const res = await pool.query(...)`<br>`res.rows[0].id` | Refactor all `POST` handlers (`properties`, `valuations`, `leads`, `users`). |
| **String Delimiters** | Double quotes tolerated: `status = "published"` | Strict single quotes: `status = 'published'` (double quotes denote column names in Postgres) | Audit all SQL strings; convert all double-quoted literals to single quotes. |
| **Unique Constraint Error** | `dbErr.code === 'ER_DUP_ENTRY'` | `dbErr.code === '23505'` (`unique_violation`) | Update error handling in `authRoutes.js` and `saved_properties`. |
| **Date / Timestamp** | `TIMESTAMP ON UPDATE CURRENT_TIMESTAMP` | `TIMESTAMPTZ` + PL/pgSQL Trigger Function | Create `trigger_set_updated_at()` and attach to relevant tables. |
| **Auto-Increment IDs** | `INT AUTO_INCREMENT` | `INTEGER GENERATED BY DEFAULT AS IDENTITY` | Allows explicit insertion of legacy IDs (1, 2, 3...) during migration. |
| **Geospatial Data** | `lat DECIMAL(10, 7), lng DECIMAL(10, 7)` | `GEOGRAPHY(Point, 4326)` + Spatial GIST Index | Native spatial calculations in meters (`ST_DWithin`). |
| **JSON Storage** | `JSON` text-based storage | `JSONB` binary format with GIN indexing | Faster containment queries (`@>`) on property amenities. |

## 3. PostGIS Correctness & Spatial Geometry Specification

### 3.1. Coordinate Order & Spatial Type Definitions
* **Coordinate Standard:** EPSG:4326 (WGS 84).
* **CRITICAL COORDINATE ORDER:** PostGIS functions `ST_MakePoint(x, y)` require `x = Longitude` and `y = Latitude`.
  - In Cairo, Egypt: Longitude is ~`31.2357° E`, Latitude is ~`30.0444° N`.
  - **Correct:** `ST_MakePoint(lng, lat)` -> `(31.2357, 30.0444)`.
  - **Incorrect:** `ST_MakePoint(lat, lng)` places the point in the Indian Ocean.
* **Coordinate Range Validation Constraints:**
  ```sql
  CONSTRAINT chk_valid_lat CHECK (lat >= -90.0 AND lat <= 90.0),
  CONSTRAINT chk_valid_lng CHECK (lng >= -180.0 AND lng <= 180.0)
  ```

### 3.2. True Geodesic (Meter-Based) Radius Queries:
In PostGIS, if `ST_DWithin` is called on two `geometry` objects in SRID 4326, the distance threshold is calculated in **degrees** (where 1° ≈ 111 km). Passing `5000` (meaning 5,000 meters) would calculate 5,000 degrees, spanning the entire planet and returning all properties.

**Validated Correction:**
We define the spatial column as a native **`GEOGRAPHY(Point, 4326)`**, or cast to `geography` within the query. This guarantees that distance comparisons are strictly evaluated in **meters**:

```sql
-- High-Performance Native PostGIS Radius Search (Unit: METERS)
SELECT id, title_en, title_ar, price, aqar_score,
       ST_Distance(location_geog, ST_SetSRID(ST_MakePoint($1, $2), 4326)::geography) AS distance_meters
FROM properties
WHERE status = 'published'
  AND ST_DWithin(location_geog, ST_SetSRID(ST_MakePoint($1, $2), 4326)::geography, $3)
ORDER BY distance_meters ASC
LIMIT $4 OFFSET $5;
```
* `$1` = Longitude (e.g. `31.4833`)
* `$2` = Latitude (e.g. `30.0167`)
* `$3` = Radius in meters (e.g. `5000` for 5 km)
* `$4` = Limit (e.g. `20`)
* `$5` = Offset (e.g. `0`)

### 3.3. Viewport Bounding-Box Map Queries:
For interactive map panning and zooming (Web & Mobile):
```sql
-- Viewport Search: Longitude between $1 and $3, Latitude between $2 and $4
SELECT id, title_en, title_ar, price, lat, lng, aqar_score, images_json
FROM properties
WHERE status = 'published'
  AND location_geog && ST_MakeEnvelope($1, $2, $3, $4, 4326)::geography
LIMIT 100;
```

## 5. Cutover Protocol & Controlled Maintenance Window (No False Claims)

### 5.1. Why True Zero-Downtime is Inappropriate for this Phase:
True zero-downtime database migration without write loss requires multi-master bidirectional Change Data Capture (CDC) via Kafka or Debezium. Implementing CDC for a 12-table platform introduces massive operational complexity and risk of replication loops.

**The Validated Industry-Standard Approach:**  
A planned, controlled **5-to-10 minute Scheduled Maintenance Window** during off-peak hours (03:00 AM Cairo Time) with a temporary HTTP 503 maintenance page.

```text
+-----------------------------------------------------------------------------------+
|                        MIGRATION TIMELINE (03:00 AM - 03:10 AM)                   |
+-----------------------------------------------------------------------------------+
| 03:00 AM: Enable Maintenance Mode in Nginx (Read-Only Banner or 503 on POST/PUT)  |
| 03:01 AM: Take authoritative final MySQL snapshot (mysqldump --single-transaction)|
| 03:02 AM: Execute automated pgloader delta migration to PostgreSQL 16             |
| 03:04 AM: Run sequence realignment script (IDENTITY sequences reset to MAX(id))  |
| 03:05 AM: Run automated data reconciliation suite (row counts & hash checks)      |
| 03:07 AM: Deploy PostgreSQL-enabled backend build (PM2 reload)                    |
| 03:08 AM: Run smoke tests against live PostgreSQL API (/health, /properties, auth)|
| 03:09 AM: Disable Maintenance Mode in Nginx -> All live traffic hits PostgreSQL   |
| 03:10 AM: Post-cutover monitoring begins                                          |
+-----------------------------------------------------------------------------------+
```

### 5.2. Sequence Realignment Verification:
After data ingestion, identity sequences must be explicitly reset so new inserts never collide with migrated IDs:
```sql
SELECT setval(pg_get_serial_sequence('users', 'id'), COALESCE((SELECT MAX(id) FROM users), 1), true);
SELECT setval(pg_get_serial_sequence('properties', 'id'), COALESCE((SELECT MAX(id) FROM properties), 1), true);
SELECT setval(pg_get_serial_sequence('location_benchmarks', 'id'), COALESCE((SELECT MAX(id) FROM location_benchmarks), 1), true);
SELECT setval(pg_get_serial_sequence('valuations', 'id'), COALESCE((SELECT MAX(id) FROM valuations), 1), true);
SELECT setval(pg_get_serial_sequence('mortgage_inquiries', 'id'), COALESCE((SELECT MAX(id) FROM mortgage_inquiries), 1), true);
SELECT setval(pg_get_serial_sequence('leads_inquiries', 'id'), COALESCE((SELECT MAX(id) FROM leads_inquiries), 1), true);
SELECT setval(pg_get_serial_sequence('professional_valuation_requests', 'id'), COALESCE((SELECT MAX(id) FROM professional_valuation_requests), 1), true);
SELECT setval(pg_get_serial_sequence('partner_applications', 'id'), COALESCE((SELECT MAX(id) FROM partner_applications), 1), true);
SELECT setval(pg_get_serial_sequence('saved_properties', 'id'), COALESCE((SELECT MAX(id) FROM saved_properties), 1), true);
```

## 6. Rollback Limitations, Realities & Disaster Recovery Plan

### 6.1. The Rollback Reality Check:
* If the backend is refactored to use PostgreSQL native drivers (`pg`) and `$1, $2` syntax, the code **cannot simply connect back to MySQL by changing `DB_CLIENT=mysql`**.
* **Validated Solution:**
  1. A dedicated Git branch `release/mysql-legacy` is preserved with the frozen, working MySQL backend.
  2. If a rollback is triggered within the 10-minute maintenance window (before DNS/Nginx traffic is reopened), reverting the codebase via `git checkout release/mysql-legacy && pm2 reload all` restores the system in **under 30 seconds with ZERO data loss**.

### 6.2. Preserving Writes Made in PostgreSQL if Rolled Back Post-Cutover:
If an issue occurs **after** production traffic is already live on PostgreSQL and new records have been created (e.g. new users or valuations):
1. Simply reverting to the old MySQL database would silently delete those new records (catastrophic write loss).
2. **Reverse Write-Replay Protocol:**
   - Every table in PostgreSQL has a `created_at` timestamp.
   - An automated delta extraction script queries all rows created after the cutover timestamp:
     `SELECT * FROM properties WHERE created_at >= '2026-10-29 03:09:00';`
   - Formats them into MySQL `INSERT` statements and replays them into MySQL before switching Nginx traffic back.

### 9.4. Application Connection Pool Budget Reassessment
* **Previous Flawed Assumption:** 4 PM2 cluster workers × 20 connections = 80 connections against a default `max_connections = 100`.
* **Identified Failure Mode:** An 80-connection allocation consumes 80% of PostgreSQL's connection budget. Adding `superuser_reserved_connections` (3), background workers (autovacuum: 3), monitoring agents (pg_isready: 2), and backup jobs (`pg_dump`: 2) leaves almost zero margin. A sudden traffic surge or worker recycle will trigger `FATAL: sorry, too many clients already`.
* **Memory Footprint Risk:** Each connection allocates memory for `work_mem = 64MB`. Under worst-case concurrent queries, 80 connections could consume up to `80 × 64MB = 5.12 GB RAM`, causing memory pressure.
* **Tuned Production Connection Budget:**
  1. Increase PostgreSQL `max_connections` to **150** in `postgresql.conf`.
  2. Configure PM2 Node.js workers to **`max: 8` connections per pool** (`4 workers × 8 = 32 connections total`).
  3. Reserve remaining 118 connections for admin CLI, migrations, monitoring, and burst traffic.
  4. Worst-case memory allocation for active connections drops to `32 × 64MB = 2.04 GB RAM`, leaving 13 GB RAM for OS and PostgreSQL cache buffers.
